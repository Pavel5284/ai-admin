# Алгоритм диалога

## 1. Граф состояний

START → INTENT
INTENT → BOOKING | RESCHEDULE | CANCEL | FAQ | HANDOFF | RESUME
BOOKING: ASK_SERVICE → (ASK_MASTER) → ASK_DATE → ASK_TIME → (OFFER_SLOTS) → ASK_CONTACT → CONFIRM → DONE
RESCHEDULE / CANCEL: FIND_BOOKING → (новое время) → CONFIRM → DONE
FAQ → ответ → RESUME («Продолжим запись?») → возврат в прерванное состояние
HANDOFF → задача оператору → DONE

Скобки означают необязательные состояния: `ASK_MASTER` пропускается, если клиент не спрашивал про мастера, а `OFFER_SLOTS` появляется, когда нужно выбрать конкретное окно из диапазона или из списка свободных.

Правило хода: после каждой реплики бот смотрит, какого слота не хватает, и спрашивает про первый недостающий (`advance`). Если клиент назвал сразу несколько слотов, лишние вопросы пропускаются.

### Фактическая реализация (сверено с `src/dialog/machine.ts`)

- `advance` — асинхронный: при `timeRange` без `time` он сразу запрашивает свободные окна и переводит в `OFFER_SLOTS`, а не спрашивает «во сколько?».
- `START` сохраняет уже распознанные слоты, даже если интент непонятен: «на завтра в 18:00» не теряется из-за слова «алло».
- В `OFFER_SLOTS` выбор «1/2/3», «первый/второй», время и «любой» разбирается отдельно; номер варианта не перезаписывает дату (флаг `choiceTurn`).
- `RESUME` возвращает в прерванное состояние и повторяет его вопрос; «нет» закрывает диалог.
- Ошибка `createBooking` очищает `outcome`, ставит `OFFER_SLOTS` и предлагает другое время. Ошибка `rescheduleBooking` сохраняет `bookingId` и `pending = 'reschedule'`, чтобы следующее «да» не создало новую запись вместо переноса. Успешный перенос очищает оба поля.
- `outcome` принимает значения `booked`, `rescheduled`, `cancelled`, `handoff`, `abandoned`, `faq_answered`, `faq_declined`; раннер считает метрики по нему.

## 2. Слоты

| Слот | Откуда берётся | Как проверяется |
|---|---|---|
| service | matchService, затем LLM | есть в таблице services |
| masterId | выбор клиента или «любой»; принимается в любой реплике | мастер делает эту услугу; если назван — окна фильтруются по нему |
| date | parseWhen, затем LLM | не в прошлом, не дальше 60 дней |
| time / timeRange | parseWhen, затем LLM | рабочие часы, слот свободен в БД |
| phone | parsePhone | формат +7, 11 цифр |
| name | реплика клиента | до 40 символов, необязателен |

## 3. Глобальные перехваты (работают в любом состоянии)

- «оператор», «человек», «администратор» → HANDOFF
- «отмена», «стоп», «не надо» → подтверждение отмены
- «повторите» → повтор последней реплики
- «назад» → вернуться к предыдущему слоту
- грубость, жалоба → HANDOFF

## 4. Паспорта состояний

Формат: спрашивает / ожидает / попутно принимает / не понял / молчит / переход.
Ниже под каждым состоянием — тот же паспорт в YAML: из него потом получаются тесты диалогов.

### START
Спрашивает: приветствие и «Чем могу помочь?». Переход: INTENT.

```yaml
state: START
ask: 'Здравствуйте! Я бот-администратор барбершопа «Борода».'
expects: [intent]
on_success: to_intent
on_not_understood: [greet_again, handoff]
```

### INTENT
Ожидает: интент (запись, перенос, отмена, вопрос, оператор). Попутно принимает: все слоты. Не понял: 1 — переспросить с примерами; 2 — предложить «записаться или задать вопрос?»; 3 — оператору. Переход: по интенту, для записи `advance`.

```yaml
state: INTENT
expects: [intent]
also_accepts: [service, date, time, phone]
on_success: by_intent        # booking → advance, faq → FAQ, cancel → FIND_BOOKING
on_not_understood:
  1: rephrase_with_examples
  2: narrow_to_two_choices
  3: handoff
```

### ASK_SERVICE
Спрашивает: «На какую услугу вас записать?» с примерами. Ожидает: service. Попутно принимает: date, time, phone. Не понял: 1 — переспросить с примером; 2 — перечислить услуги списком; 3 — оператору. Молчит: напомнить → повторить короче → закрыть, слоты сохранить.

```yaml
state: ASK_SERVICE
ask: 'На какую услугу вас записать? Например: мужская стрижка или оформление бороды.'
expects: [service]
also_accepts: [date, time, phone]
on_success: advance
on_not_understood:
  1: rephrase_with_example
  2: list_services
  3: handoff
on_silence: [remind, repeat_short, close_keep_slots]
```

### ASK_MASTER (необязательное)
Спрашивает: «К какому мастеру? Можно к любому свободному». Ожидает: masterId или «любой». Если клиент не назвал, берём «любой». Не понял: считаем «любой». Состояние достигается, когда клиент сам спрашивает «к кому записать?»; названного мастера можно указать в любой реплике — слот подхватывается на лету.

```yaml
state: ASK_MASTER
ask: 'К какому мастеру записать? Можно к любому свободному.'
expects: [masterId]
also_accepts: [any_master]
on_success: advance
on_not_understood: [take_any_master]
```

### ASK_DATE
Спрашивает: «На какой день вас записать?». Ожидает: date. Попутно принимает: time, timeRange, service. Не понял: 1 — пример «завтра» или «в субботу»; 2 — варианты «завтра, послезавтра, ближайшая суббота»; 3 — оператору. Неоднозначная дата («на следующей неделе») — уточнить, слот не заполнять.

```yaml
state: ASK_DATE
ask: 'На какой день вас записать?'
expects: [date]
also_accepts: [time, timeRange, service]
on_success: advance
on_not_understood:
  1: rephrase_with_example
  2: offer_three_days
  3: handoff
on_ambiguous: clarify_date     # «на следующей неделе» → уточнить, слот не ставим
```

### ASK_TIME
Спрашивает: «На какое время?». Ожидает: time или timeRange. Попутно принимает: date. Не понял: 1 — пример «в шесть вечера» или «после обеда»; 2 — «утро, день или вечер?»; 3 — оператору. Неоднозначное время («в десять») — уточнить.

```yaml
state: ASK_TIME
ask: 'На какое время?'
expects: [time, timeRange]
also_accepts: [date]
on_success: advance_or_offer_slots
on_not_understood:
  1: rephrase_with_example
  2: offer_morning_day_evening
  3: handoff
on_ambiguous: clarify_time
```

### OFFER_SLOTS
Показывает до трёх свободных слотов. Ожидает: выбор (номер, время или «любой»). Нет слотов в этот день → ближайшие дни или другой мастер. Не понял: 1 — повторить варианты; 2 — предложить другой день; 3 — оператору.

```yaml
state: OFFER_SLOTS
ask: 'Свободное время {день}: 1) …, 2) …, 3) …. Какое выбираете?'
expects: [slot_choice]
also_accepts: [time]
on_success: advance
on_not_understood:
  1: repeat_options
  2: offer_other_day
  3: handoff
on_no_slots: offer_other_day
```

### ASK_CONTACT
Спрашивает: «Назовите номер телефона». Ожидает: phone (name — по желанию). Неполный номер копится в phoneDraft и клиенту сообщается, сколько цифр записано. Слишком длинный — попросить повторить. Не понял: 1 — продиктовать цифрами; 2 — по частям; 3 — оператору.

```yaml
state: ASK_CONTACT
ask: 'Назовите, пожалуйста, номер телефона для записи.'
expects: [phone]
also_accepts: [name]
on_success: advance
on_partial: keep_digits_and_ask_more      # «Записал 6 цифр из 11. Продолжайте.»
on_too_long: reset_draft_and_ask_again
on_not_understood:
  1: ask_digits_slowly
  2: ask_in_parts
  3: handoff
```

### CONFIRM
Зачитывает: услугу, дату словами, время, мастера, телефон. Ожидает: «да» или «нет». «Да» → create_booking. «Нет» → «Что изменить?» и возврат к нужному слоту. «Да, но…» не считается подтверждением.

```yaml
state: CONFIRM
ask: 'Проверим запись: {услуга}, {дата}, {время}, {мастер}, {телефон}. Всё верно?'
expects: [yes, no]
on_yes: create_booking
on_no: ask_what_to_change        # → CONFIRM с pending = change
on_not_understood: [ask_yes_or_no, handoff]
```

### FIND_BOOKING (перенос и отмена)
Ищет записи по телефону в БД (`findBookingsByPhone`). Ноль записей → предложить новую запись или оператора. Несколько → попросить выбрать номер записи. Далее перенос идёт через ASK_DATE и ASK_TIME, отмена — через подтверждение CONFIRM. Отмена и перенос — отдельные действия (`cancel_booking`, `reschedule_booking`), которые выполняет `src/services/actions.ts`.

```yaml
state: FIND_BOOKING
ask: 'Назовите номер телефона, по которому ищем запись.'
expects: [phone]
also_accepts: [cancel, reschedule]
on_success: found_booking        # → CONFIRM (отмена) или ASK_DATE (перенос)
on_not_found: offer_new_booking_or_operator
on_several: ask_which_booking
on_not_understood: [ask_phone_again, handoff]
```

### FAQ
Ищет ответ по базе знаний. Ответ найден → ответить и спросить «Продолжим запись?». Ответа нет → «Уточню у администратора», задача оператору, возврат в прерванное состояние.

```yaml
state: FAQ
ask: null                        # бот не задаёт вопрос, а отвечает
expects: [question]
on_answer: answer_and_ask_continue
on_not_found: no_answer_and_task_to_operator
on_resume: continue_interrupted_state
```

### RESUME
Бот ответил на вопрос посреди записи и ждёт «продолжим?». «Да» → вернуться в прерванное состояние и повторить его вопрос. «Нет» → вежливо завершить диалог.

```yaml
state: RESUME
ask: 'Продолжим запись?'
expects: [yes, no]
on_yes: ask_again_interrupted_state
on_no: close_politely
```

### HANDOFF
Сообщает клиенту, что передаёт администратору, создаёт задачу с последними репликами. Переход: DONE.

```yaml
state: HANDOFF
ask: 'Передаю вас администратору, он свяжется с вами в ближайшее время.'
expects: []
on_enter: create_operator_task
on_success: to_done
```

### DONE
Сессия закрыта. Следующее сообщение клиента начинает новую сессию.

```yaml
state: DONE
ask: null
expects: []
on_success: start_new_session
```

## 5. Нештатные ситуации

Каждая строка таблицы раздела 2.6 гайда закрыта своим диалогом; ядро проверяется
в `tests/unit/edge-cases.test.ts` (12 сценариев), полные диалоги — в `tests/dialogs/*.yaml`
(97 сценариев, включая 110–114 для сбоев систем).

| Ситуация | Как обнаруживается | Реакция бота | Пример |
|---|---|---|---|
| Не понял | NLU не заполнил ожидаемый слот | 1 — переспросить с примером, 2 — сузить вопрос, 3 — оператору | «хочу записаться» → «абракадабра» → «что-то» → «ерунда» |
| Молчит | событие `silence` | 1 — «Вы здесь?», 2 — повторить короче, 3 — закрыть, слоты сохранить | «стрижка» → /silence ×3 |
| Перебил | событие `barge_in` | замолчать, разобрать реплику как обычный ввод | «хочу записаться» → /barge «стрижка» |
| Поправил себя | маркер «нет, …» в реплике | взять последнее значение, слот перезаписать | «завтра, нет, в четверг» → четверг |
| Ответил не на тот вопрос | в реплике слот другого типа | принять слот, спросить про свой | «в 18:00» в состоянии ASK_DATE |
| Вопрос не по теме | интент FAQ посреди записи | ответить, задача оператору, «Продолжим запись?» | «сколько стоит стрижка?» → RESUME |
| Передумал | «не надо», «отмена», «стоп» | подтвердить отмену, очистить слоты | «стоп» → «да» |
| Нет свободных слотов | пустой результат из БД | предложить соседние дни и другого мастера | `nearestSlots` в `src/services/slots.ts` |
| Слот заняли, пока клиент думал | ошибка при создании записи | извиниться, вернуться к OFFER_SLOTS | ограничение `EXCLUDE` в БД, код `23P01` ловится в `createBooking` |
| CRM недоступна | таймаут/5xx при заявке | запись остаётся в БД, заявка уходит в `crm_outbox` | сценарии 110, 111 |
| LLM недоступна | таймаут/429/5xx | правила доводят диалог или честный отказ | сценарий 113 |
| База знаний недоступна | ошибка эмбеддингов/БД | «уточню у администратора», задача оператору | сценарий 114 |
| Агрессия, жалоба | словарь жалоб | сразу оператору, из любого состояния | «это жалоба, вы ужасны» |
| Две просьбы в одной реплике | два интента | сначала вопрос, потом запись | «хочу записаться на стрижку, сколько стоит стрижка?» |
| Голосовое, фото, стикер | тип сообщения в Telegram | попросить написать текстом | ядро и Telegram-канал умеют (событие `non_text`) |
| Дата в прошлом | разбор даты дал прошлый день | уточнить дату, слот не заполнять | «вчера» |
| Дата дальше горизонта | разбор даты дал дату дальше 60 дней | уточнить дату, слот не заполнять | «1 января» |

Отклонения от таблицы гайда: неоднозначная дата («на следующей неделе») и
неоднозначное время — бот задаёт уточняющий вопрос и **не заполняет слот**,
чтобы клиент не записался не туда.
