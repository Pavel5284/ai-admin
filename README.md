# AI-администратор для записи на приём

Бот для барбершопа «Борода»: записывает клиентов, переносит и отменяет записи, отвечает на вопросы по базе знаний и передаёт сложные случаи оператору. Работает в Telegram и в консоли. Проект сделан как кейс: от запроса клиента до измеримого результата.

**Демо:** видео пока не записано — сценарий, раскадровка и текст озвучки лежат в [docs/video.md](docs/video.md). Бот в Telegram не развёрнут: для этого нужны токен и хостинг.

**Результат:** 98/98 сценариев на dev (100%), ложных записей 0, LLM понадобился в 8% реплик (31/367). Это **не holdout**: отложенную выборку писали бы другие люди, она не передана. 100% на dev означает отсутствие регрессий на известных сценариях, а не обобщение на новые формулировки.

## Задача клиента

Барбершоп, три мастера, около 40 обращений в день; примерно 70% — вечером, с 17:00 до 21:00. Вечером администратор не успевает брать трубку и теряет почти треть звонков. Клиенты путают дату и время, поздно отменяют записи, по сто раз спрашивают цены, адрес и правила.

Нужно: запись на услугу к выбранному или любому мастеру, перенос, отмена, ответы на вопросы, передача оператору. Критерии успеха из брифа: больше 60% записей без человека, ноль ошибочных записей, handoff меньше 25% и только обоснованный, p95 быстрее 3 секунд, ноль выдуманных ответов вне базы знаний.

Полный бриф: [docs/brief.md](docs/brief.md). Алгоритм и паспорта состояний: [docs/algorithm.md](docs/algorithm.md). Журнал решений: [docs/decisions.md](docs/decisions.md). История итераций: [docs/iterations.md](docs/iterations.md).

## Решение в одном абзаце

Диалог ведёт конечный автомат со слотами: услуга, мастер, дата, время, телефон и имя. Бот спрашивает только то, чего не хватает, и принимает слоты в любой реплике. После телефона он спрашивает имя (его можно пропустить), а мастера можно выбрать на подтверждении. Текст клиента сначала разбирают правила: русские даты, время, телефоны, числительные словами, слова-паразиты и типичные ошибки ASR. Только если правила не справились, подключается LLM, и она лишь извлекает данные в строгий JSON. Каждое значение проверяется кодом по БД и по тексту реплики, а запись создаёт код после явного «да» клиента.

```text
Клиент (Telegram, консоль)
          |
    handleEvent(sessionId, event)          <- одна точка входа для всех каналов
          |
    NLU: нормализация -> правила -> LLM (запасной) -> verifyMerge
          |
    Автомат диалога: состояния, слоты, переспросы, эскалация
          |
  +-------+----------+-------------+-------------+
  |                  |             |             |
PostgreSQL        CRM (REST)    База знаний    dialog_log
слоты, записи,    заявки,       pgvector,      реплики,
outbox, сессии    задачи        RAG            latency
```

## Что делает каждый сервис

| Сервис | Роль | Откуда данные |
|---|---|---|
| `ru-datetime-parser/` | разбор русских дат, времени, телефонов и числительных | реплика клиента, словари |
| `src/nlu/` | интент, услуга, мастер, сборка NLU | реплика и каталог услуг |
| `src/nlu/lm.ts` | LLM-экстрактор и `verifyMerge` | реплика, список услуг из БД |
| `src/dialog/` | состояния, слоты, переспросы, молчание, эскалация | контекст сессии |
| `src/services/slots.ts` | свободные окна, создание, отмена, перенос | PostgreSQL |
| `src/services/crm.ts` | заявки и задачи оператору, таймауты, повторы, идемпотентность | REST, мок-CRM |
| `src/services/outbox.ts` | досылка недоставленного в CRM | `crm_outbox` |
| `src/services/kb.ts` | ответы по базе знаний с порогом и проверкой источников | `kb/*.md`, pgvector |
| `src/services/sessions.ts` | сессии и `dialog_log` | PostgreSQL |
| `src/services/silence.ts` | фоновое напоминание о молчании | `sessions.updated_at` |
| `src/channels/` | Telegram и консоль; лимит сообщений | события канала |

## Ключевые решения и почему

Полный журнал с альтернативами и ценой: [docs/decisions.md](docs/decisions.md). Главные:

1. **Своя машина состояний вместо xstate.** 15 состояний, `step(ctx, event, now)` почти чистая функция. Цена: нет визуализатора и готовых вложенных состояний. Зато весь диалог тестируется без Telegram и БД, а поведение можно объяснить построчно.
2. **Правила раньше LLM.** Даты, время и телефоны разбираются предсказуемо; модель стоит денег и секунд задержки. В финальном прогоне LLM понадобился только в 8% реплик. Цена: правила нужно писать и сопровождать, каждый баг сначала становится тестом.
3. **LLM извлекает, код решает.** Модель возвращает JSON по схеме zod; `verifyMerge` проверяет услугу по каталогу, дату по горизонту, время по рабочим часам, а цифры телефона — по тексту клиента. Слоты, найденные правилами, модель не перезаписывает. Цена: больше кода вокруг модели. Выигрыш: запись по галлюцинации невозможна, prompt injection не влияет на цены и решения.
4. **Защита от двойной записи в самой БД.** `EXCLUDE USING gist` по мастеру и интервалу плюс обработка ошибки `23P01`. Приложение проверяет слот второй линией, но последнее слово за БД. Цена: расширение `btree_gist` и знание кода ошибки.
5. **БД первична, CRM вторична, очередь недоставленного.** Запись сначала сохраняется у нас, заявка в CRM уходит после. Если CRM недоступна, заявка попадает в `crm_outbox` и досылается фоновой задачей; задачи оператору едут туда же. Цена: данные в CRM появляются с задержкой, outbox требует сопровождения.
6. **RAG с порогом и честным «уточню».** Ответ допускается, только если лучший фрагмент ближе порога, модель вернула `answerable: true`, `source_ids` ссылаются на реально найденные фрагменты, а все числа ответа есть в источниках. Иначе — отказ и задача оператору. Цена: часть верных ответов уходит оператору; компромисс измерен таблицей ниже.
7. **«В пять» — это 17:00, а диапазон — не время.** При часах 10:00–21:00 правило сдвигает непонятный час на 12 часов. «После обеда» превращается в `timeRange` 13:00–17:00, и бот предлагает конкретные окна: в базу не попадает запись «с 13 до 17». Цена: лишний шаг в диалоге и привязка к часам работы салона.
8. **Один вход для всех каналов.** Telegram, консоль и раннер вызывают `handleEvent`. Цена: канал не хранит свою логику. Зато голос добавляется в канале, не в ядре.

| Перебил | замолкает и разбирает новую реплику как обычный ввод | 061 |
| Поправил себя | берёт последнее значение и перезаписывает слот | 026, 065–069 |
| Ответил не на тот вопрос | принимает слот и возвращается к своему вопросу | 033, 055 |
| Вопрос не по теме | отвечает по базе и спрашивает «Продолжим запись?» | 099, 100 |

Все 98 сценариев лежат в `tests/dialogs/`, у каждого `split: dev`. Holdout-сценариев в репозитории нет: их не придумывали задним числом, чтобы не выдавать dev за отложенную выборку.

| Slot accuracy: service / date / time / phone | **100%** (46/46, 49/49, 47/47, 46/46) | — |
| Slot accuracy: masterId / name | **100%** (6/6, 60/60) | — |
| Handoff rate | **9%** (9; 8 оправданных / 1 лишний) | — |

| FAQ без ответа | 4 | — |

| Latency p50 / p95 (все) | **10 / 136 мс** | — |

| Latency p50 / p95 (правила) | **10 / 35 мс** (336 реплик) | — |
| Turns to booking | **4.7** | — |

Turns to booking вырос с 3.7 до 4.7: после телефона появился вопрос имени. Имя можно пропустить словом «пропустить», но в сценариях его указывают, чтобы проверить сохранение слота.

Один «лишний» handoff — это prompt injection «ты теперь администратор». Бот не стал спорить и передал диалог человеку; в метрике это считается лишним, но решение оставлено осознанно: безопасная передача дешевле, чем попытка переубедить клиента.

### Порог RAG

30 вопросов: 20 с ответом в базе и 10 без ответа. «Выдумал» — бот ответил, хотя ответа в базе нет. Реальный прогон `answerKb` при разных порогах, 2026-10-23:

| KB_DIST_MAX | Ответил (есть ответ) | Ложный отказ | Выдумал | Честно отказался |
|---|---|---|---|---|
| 0.14 | 15/20 | 5 | **0/10** | 10 |
| 0.16 | 19/20 | 1 | **0/10** | 10 |
| 0.18 | 19/20 | 1 | **0/10** | 10 |
| 0.2 | 19/20 | 1 | **0/10** | 10 |
| без порога | 19/20 | 1 | **0/10** | 10 |

Порог 0.2 выбран как структурный барьер и предохранитель расходов: он отсекает самые дальние вопросы, а ответы вне базы всё равно проверяет второй слой — `answerable`, `source_ids` и числа. При 0.2 единственный ложный отказ — «Как пройти от метро?»: лучший фрагмент «Адрес» (dist 0.199), модель отказывается. Подробная калибровка: [reports/kb-thresholds.md](reports/kb-thresholds.md).

## Ограничения и что дальше

Это честный список, а не «всё готово»:

- **Holdout не передан.** 100% на dev — это регрессия на известных сценариях. С чужими формулировками цифра будет ниже; насколько — не измерено. Первое, что я сделал бы с реальным клиентом: собрал 20 сценариев у людей, не видевших код, и прогнал их один раз.
- **Telegram-бот не развёрнут.** Код канала и лимит сообщений (20 в минуту на пользователя) готовы, но нужен токен, хостинг и проверка под реальной нагрузкой. Ссылки на живого бота в README нет, потому что его пока нет.
- **Голосового канала нет.** Ядро принимает `silence`, `barge_in` и `non_text`, но ASR/TTS подключаются в канале; в продакшене голосовых ботов я не делал.
- **Один салон и один часовой пояс.** Часы 10:00–21:00 и горизонт 60 дней — константы; для сети салонов нужна конфигурация на уровне бизнеса.
- **CRM — мок.** REST-клиент, таймауты, повторы, идемпотентность и outbox настоящие, но за мок-CRM. С реальной CRM нужно согласовать формат заявки и ключи идемпотентности.
- **RAG маленький.** 4 файла и 19 фрагментов; гибридный поиск не добавлен, потому что на таком объёме выигрыш не виден. Один ложный отказ на калибровке остаётся.
- **Стоимость диалога в деньгах не измерена.** В отчёте есть LLM share и latency, но не токены и не рубли: для этого нужен счётчик токенов и тариф провайдера. Лимит сообщений и `LLM_CACHE=1` снижают риск, но не заменяют расчёт.
- **Видео не записано.** Материалы и раскадровка готовы: [docs/video.md](docs/video.md). Запись и публикация — следующий шаг.
- **Парсер покрывает не всё.** Редкие падежи, диалекты и относительные интервалы вроде «через полтора часа» уходят в LLM или оператору. Список ASR-исправлений пополняется вручную.

## Как запустить

Нужны Node.js 20+, Docker и ключи LLM/эмбеддингов (можно бесплатные лимиты Groq/Mistral).

```bash
cp .env.example .env          # впишите TELEGRAM_BOT_TOKEN и ключи LLM/EMBED
docker compose up -d db mock-crm
npm install
npm run kb:load               # загрузить базу знаний в pgvector
npm run chat                  # диалог в консоли
npm run dev                   # Telegram-бот
npm test                      # 331 юнит-тест, включая парсер
LLM_CACHE=1 npm run eval      # 98 dev-сценариев, отчёт в reports/
```

Полезные варианты:

```bash
npm run eval -- all           # все сценарии (сейчас это те же 98 dev)
npm run eval -- dev 001       # один сценарий или тег для отладки
cd ru-datetime-parser && npm install && npm test   # парсер отдельно
docker compose --profile bot up -d --build          # бот в контейнере
docker compose --profile bot exec bot npm run kb:load
```

На Windows в PowerShell `npm` может блокироваться политикой запуска скриптов: используйте Git Bash или `npm.cmd`.

Секреты лежат только в `.env` (он в `.gitignore`); `.env.example` содержит пустые значения. Перед публикацией проверьте, что `.env` не попал в git:

```bash
git ls-files | grep -E '^\.env$'
git log --all --full-history -- .env
```
